# Data Model — v0.1

This document describes the logical data model. The authoritative SQL is
[`backend/migrations/0001_init.sql`](../../backend/migrations/0001_init.sql).

## Entities

```
organizations 1───n users
organizations 1───n agents
organizations 1───n agent_enrollment_tokens
organizations 1───n certificates
organizations 1───n findings
organizations 1───n providers
organizations 1───n audit_events

certificates 1───n certificate_observations
agents       1───n certificate_observations

certificates 1───n findings
users        1───n sessions
```

## Identifiers

All entities use opaque `TEXT` identifiers generated by `internal/ids`. We
deliberately keep the format opaque so the underlying scheme (currently
random hex; UUIDv7 in Phase 1) can change without API breakage.

## Multi-tenancy (limited)

A single `organizations` row is created at first boot. Every domain table
has an `organization_id` foreign key today so that future multi-tenant
isolation does not require a schema rewrite. **v0.1 does not enforce
cross-org isolation in code beyond this column.**

## Insert-Only Tables

- `audit_events` — protected by triggers that reject `UPDATE` and `DELETE`.
- `certificate_observations` — logically append-only; superseded rows are
  identified by the `(certificate_id, agent_id, store_location)` unique
  key plus `observed_at` timestamps.

## Sensitive Data

- `users.password_hash` — bcrypt; never logged, never returned by the API.
- `agent_enrollment_tokens.token_hash` — SHA-256 of the issued token. The
  raw token is shown to the operator **once** at issuance and discarded.
- `sessions.id` — opaque server-side session id; the cookie carries a
  signed reference, not the raw id.
- `certificates.pem` — **public** certificate PEM only. The schema has
  no column for private key material; ingestion code rejects payloads
  that contain any (CLAUDE.md §6.2).

## Indexes

Each table has indexes appropriate to its access patterns (see migration
file). The biggest expected hot paths in v0.1:

- `certificates` filtered by `organization_id, not_after` (expiring soon).
- `findings` filtered by `organization_id, status, severity`.
- `audit_events` filtered by `organization_id, occurred_at DESC`.

## Future Evolution

- `organization_id` foreign keys make multi-tenancy a code change, not a
  schema change.
- `providers.config` is `JSONB` so per-provider settings evolve without
  schema migrations for additive changes.
- `findings.evidence` is `JSONB` so rules can attach arbitrary structured
  evidence without a new column per rule.
